# Architecture Checklist

## When to Use

- 需要使用 architecture-checklist 時

在設計或審查系統架構時，按以下清單逐項檢查，避免常見的設計疏漏。

---

## 1. 資料生命週期 (Data Lifecycle)

### 創建 (Create)

- [ ] **即時持久化**：資料創建後是否立即寫入資料庫？還是只存在記憶體中？
- [ ] **失敗處理**：寫入失敗時，前端狀態如何回滾？
- [ ] **預設值**：所有必填欄位是否都有合理的預設值？
- [ ] **唯一性**：是否需要檢查唯一性約束（如 email、username）？

### 讀取 (Read)

- [ ] **查詢完整性**：`orderBy` / `where` 條件是否會意外排除沒有該欄位的文件？
- [ ] **空值處理**：欄位為 `null`/`undefined` 時，UI 如何顯示？
- [ ] **分頁**：大量資料是否有分頁或虛擬滾動機制？

### 更新 (Update)

- [ ] **部分更新**：使用 `merge: true` 還是完整覆蓋？
- [ ] **樂觀更新**：前端是否先更新 UI，再等待後端確認？
- [ ] **並發衝突**：多人同時編輯同一筆資料時如何處理？

### 刪除 (Delete)

- [ ] **軟刪除 vs 硬刪除**：是否需要保留歷史記錄？
- [ ] **關聯資料**：刪除父記錄時，子記錄如何處理（級聯刪除？孤兒記錄？）

---

## 2. 前後端狀態同步 (State Synchronization)

### 新用戶/新資源流程

- [ ] **資料庫記錄創建時機**：用戶首次登入時，是否立即在資料庫創建記錄？
  - ⚠️ **常見錯誤**：只在前端記憶體創建物件，導致後台查詢不到
- [ ] **不完整資料處理**：用戶中途放棄流程時，系統狀態是否一致？

### 即時同步

- [ ] **監聽器**：使用 `onSnapshot` 還是單次 `getDoc`？
- [ ] **離線支援**：離線時的本地快取策略？

### 狀態映射

- [ ] **枚舉值對應**：前端顯示的狀態標籤是否與後端值完全對應？
  - ⚠️ **常見錯誤**：後端是 `'pending'`，前端判斷用 `'Pending'`（大小寫不符）
- [ ] **Fallback 顯示**：當狀態值為 `undefined` 時，UI 顯示什麼？這是否符合業務邏輯？

---

## 3. 認證與授權 (Auth & Authorization)

### 認證流程

- [ ] **Token 過期**：JWT/Session 過期時的自動刷新或重新登入提示
- [ ] **多裝置登入**：是否允許？如何處理衝突？
- [ ] **登出清理**：登出時是否清除所有本地狀態和快取？

### 授權檢查

- [ ] **前端路由守衛**：是否只做 UI 隱藏，還是真正阻擋導航？
- [ ] **PWA / 公開路由非阻塞**：`router.beforeEach` 對於 `meta.public` (如 Login/Lookup) 必須優先秒開放行，非同步 Auth 握手 (`initAuth`) 轉至背景執行，嚴禁同步 `await` 導致冷啟動 5~10 秒白屏。
- [ ] **全站單一版本源頭 (Single Version Source)**：版本號統一由 `src/config/version.ts` 匯出，禁止在組件寫死版本字串。
- [ ] **後端規則**：Firebase Security Rules / API 權限是否與前端邏輯一致？
- [ ] **角色變更即時性**：管理員修改用戶權限後，用戶端是否處理更新？

---

## 4. 篩選與查詢邏輯 (Filtering & Queries)

### 條件篩選

- [ ] **缺失欄位**：篩選條件是否處理欄位不存在的情況？

  ```typescript
  // ❌ 錯誤：status 為 undefined 時被排除
  users.filter((u) => u.status === "active");

  // ✅ 正確：向後相容
  users.filter((u) => u.status === "active" || !u.status);
  ```

- [ ] **邊界值**：空字串、0、false 是否被當作「無值」處理？

### 排序

- [ ] **Firestore orderBy**：會自動排除沒有排序欄位的文件，這是期望行為嗎？
- [ ] **Null 值排序**：null 值應該排在最前還是最後？

---

## 5. 錯誤處理 (Error Handling)

### 網路錯誤

- [ ] **重試機制**：是否有指數退避重試？
- [ ] **離線提示**：是否清楚告知用戶目前離線？

### 業務錯誤

- [ ] **用戶友善訊息**：是否將技術錯誤碼轉換為用戶可理解的訊息？
- [ ] **錯誤上報**：是否記錄到 Sentry/LogRocket 等監控服務？

---

## 6. 邊界情況 (Edge Cases)

### 用戶行為

- [ ] **中途放棄**：用戶在多步驟流程中關閉頁面
- [ ] **重複提交**：快速點擊按鈕兩次
- [ ] **瀏覽器返回**：按返回鍵時的狀態處理
- [ ] **Tab 切換**：長時間切換到其他 Tab 後返回

### 資料狀態

- [ ] **空列表**：列表無資料時的 UI 呈現
- [ ] **單項 vs 多項**：只有一筆資料時的特殊處理
- [ ] **超長內容**：文字過長時的截斷或換行

---

## 7. 效能考量 (Performance)

### 查詢優化

- [ ] **N+1 問題**：是否在迴圈中發送查詢？
- [ ] **索引**：常用查詢是否有適當的 composite index？

### 渲染優化

- [ ] **虛擬化**：長列表是否使用虛擬滾動？
- [ ] **Memo 化**：頻繁重新渲染的元件是否使用 `useMemo`/`React.memo`？
- [ ] **FCM Multicast 500 筆分塊防護**：呼叫 `messaging.sendEachForMulticast` 時，強制以 500 筆為單位進行 Chunking 分段發送，並帶入 Document ID 直接清除無效 Token。
- [ ] **防弊 Trigger 使用 `onDocumentWritten`**：計費與安全性自動覆核 Cloud Functions，禁止僅使用 `onDocumentCreated`，必須使用 `onDocumentWritten` 並比對 `before/after` 資料差異，防止二次竄改漏洞。

---

## 使用方式

在設計新功能或 code review 時：

1. 識別功能類型（認證、CRUD、狀態管理等）
2. 對照相關章節的 checklist
3. 針對每一項確認是否已處理
4. 特別注意有 ⚠️ 標記的常見錯誤

> [!IMPORTANT]
> 這份 checklist 不是要每次都全部檢查，而是針對**相關**的項目進行確認。新功能開發時，重點檢查「資料生命週期」和「前後端狀態同步」章節。
